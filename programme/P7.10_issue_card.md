## The design decision, and why

**D32 is repaired by canonicalising the accumulation ORDER, never by rounding.** The brief forbade "fixing" the drift by rounding to the tolerance, and rightly: the tolerance is `max(0.01, |anchor| * 1e-9)` and rounding to it would destroy the very digits a tightened tolerance would later need. `scripts/lib/canonical_sum.mjs` instead sums a multiset of doubles in an order derived only from the values themselves, so no traversal order can reach the result. The reported residual for seed 700577 is UNCHANGED at `-943.56`; what changed is that the reversed register now also reports `-943.56`.

**Why the invariance is proved rather than asserted.** The proof is four steps, written out in the module header:
1. `canonicalSum` never reads the caller's order — it sorts, then folds left from `+0`.
2. Sorting a multiset with a TOTAL order yields a sequence unique up to permutation of comparator-equal elements.
3. `compareCanonicalAddend` returns `0` only for BIT-IDENTICAL doubles: it orders by value, breaks the single remaining IEEE-754 tie (`-0` vs `+0`) by sign bit, and pins `NaN` to a fixed end. Its equality class is therefore a singleton per bit pattern. This clause is separately asserted in the suite, because it is the load-bearing one — if two distinct bit patterns ever compared equal, the sorted sequence would stop being unique and the whole argument would collapse.
4. Permuting bit-identical addends cannot change a partial sum.

The shuffle test is corroboration, not the proof — and it is written so it cannot pass vacuously: the same 500 permutations are also folded naively, and the check FAILS unless the naive fold disagrees with itself.

**`canonicalSum` throws on a non-number addend instead of coercing it.** An order-invariant sum that silently read absent as `0` would just be a deterministic never-zero bug. Invariant 1 therefore guards invariant 2's entry point: `canonicalSum([1, null, 2])` throws rather than returning 3. This is the only place in this package where the two invariants meet in code, and it is deliberate.

**D31 is NOT repaired here, and the reason is not squeamishness about the rule.** Every route to the mint runs through `solver.mjs`: `statement_values` is written at exactly one place (`solver.mjs:3334`, `Object.fromEntries(finalStatementValues)`), fed by exactly one place (`resolveAll()` at `solver.mjs:956`, which resolves EVERY definition including headers), and the zero is produced at exactly one place (`statementRowForecastValue`'s `if (authority.mechanism === "uncalculated" || authority.mechanism === "zero") return 0`). The only non-solver lever would be to stop headers entering `normaliseStatementRows`' output — that is `row_plan.mjs`, also forbidden, and it would be the wrong repair anyway because headers are needed for rendering. The package therefore stops, specifies the patch, and locks the defect's exact extent so it cannot widen unnoticed.

### D31's asymmetry, explained — and the registered description is incomplete

The register says "the LEADING header appears and the trailing one does not". That is true of the income statement and FALSE of the cash flow: `hdr.cash-flow-repeat` is also a trailing header and it DOES appear. The rule is not about position.

Tracing `normaliseStatementRows` on the transformed case:

```
income_statement IN : hdr.income-statement | revenue | net_income | non_controlling_interests | owners_of_parent | hdr.income-statement-repeat
income_statement OUT: hdr.income-statement | revenue | net_income | adjusted_ebitda_bridge | non_controlling_interests | owners_of_parent
cash_flow        IN : hdr.cash-flow | capex | hdr.cash-flow-repeat
cash_flow        OUT: hdr.cash-flow | capex | hdr.cash-flow-repeat
```

`projectIncomeStatementToDebtOverlay` (`row_plan.mjs:2711-2725`) slices the income statement at net income, splits everything AFTER it into header-led blocks, and DROPS any block holding no required row. The trailing header is a block of one header and zero required rows, so it is pruned before the solver ever sees it; the leading header sits in the un-pruned `beforeAndIncludingNetIncome` slice. The cash flow runs no such projection, so both of its headers survive.

**So survival is asymmetric; minting is not.** Every header that reaches the solver's statement graph is minted. That distinction matters because it changes the defect's size: the asymmetry is a row-pruning artefact in `row_plan.mjs`, while the coercion is an unconditional property of `solver.mjs`.

And the extent is larger than registered in a second way. The same normaliser INSERTS a header — `adjusted_ebitda_bridge` (`row_plan.mjs:2420`) — into the UNTRANSFORMED archetype, and it is minted as `0` in the baseline solve:

```
BASELINE header row adjusted_ebitda_bridge -> statement_values = 0
   authority: { method: "not_applicable", mechanism: "uncalculated",
                reason: "Presentation-only header.", declared_value: null, value: null }
```

The forecast-authority layer resolves NO number and says so in three fields. The solver overrides all three with a literal `0`. **MG-4 is therefore not a defect the metamorphic transform introduces — the transform only made a pre-existing mint visible as a delta.** Across the solvable archetype corpus and a 24-seed generated cohort, the escape rate is exactly zero: every valueless header that reaches the solver is minted, none escapes. That is what the suite's extent lock asserts.

### Why the class keeps re-opening — the structural answer

D11 (never-zero coercions in opening-instrument provenance), D6 (a printed dash left ABSENT escaping the footing pass) and D31 are not three unrelated bugs. The repository has a correct, complete typed value model — `typed_financial_value.mjs` with 12 states, 4 value-bearing and 8 never-zero; `typed_arithmetic.mjs`, which returns `unresolved` for an absent operand; `source_tolerance.filedNumber`, which returns `null` for `null`/`""`/boolean/non-finite. **Nothing on the live numeric spine imports any of them.** `typed_financial_value.mjs` is imported by 7 modules, all of them peripheral. `typed_arithmetic.mjs` is imported by ZERO production modules — only two test runners. None of `solver.mjs`, `row_plan.mjs`, `case_compiler.mjs`, `canonical_model_modules.mjs`, `fixed_point_constitution.mjs`, `forecast_authority.mjs` or `attachment_ingress.mjs` imports any of them.

The doctrine exists as a shadow core beside the spine that actually computes the numbers. So each defect in this class is found where it happens to be looked for, is repaired at that point, and the mechanism that produced it — an untyped numeric layer whose default for absence is a literal — is untouched. That is why a point fix closes an instance and never the class, and it is why this is the third instance rather than the last. A single structural repair is available in principle (route the three absent-to-number funnels — `solver.asSeries3`, `instrument_period_state.series3`, `forecast_authority.rankNumber` — through `filedNumber` and let `null` propagate, which converts roughly 120 downstream `?? 0` sites from silent-zero to visible-absence), but it lands in forbidden files and is a Phase 9 decomposition, not a surgical repair. It is recorded here so the freeze knows what it is carrying.
