## What the cross-layer edges bind, and why these pairs

`ECONOMIC_STATEMENT_BINDING` declares one entry per equation-graph node — 39 entries for 39 nodes, exact set equality enforced at import — in three dispositions: **18 `statement_row`**, **20 `schedule_row`**, **1 `solver_control`**. A `statement_row` entry names the (`section`, `semantic_role`) pair that realises the node, and the compiler emits a `realises_statement_row` cross-layer edge from `economic:<node>` to `statement:<section>:<row_id>:0` whenever that row is present. Both certified fixtures compile **17 cross-layer edges** (the eighteenth, `cash.noncash_interest_addback`, is `row_absent` — neither fixture files a `non_cash_interest_addback` row, which is a lawful case variant and is recorded rather than blocked).

The pairs are not invented here. `join_basis: "model_ir_crosswalk"` reproduces the binding `model_ir_v3.mjs:1315-1412` has been using all along to build the workbook proof contract — including the three that a name match would have got WRONG: `statement.cash_flow_start` → `cash_flow_net_income`, `statement.finance_expense` → `interest_expense`, `statement.finance_income` → `interest_income`. `join_basis: "role_identity"` means the equation role and the statement `semantic_role` are the same declared token; `join_basis: "etr_path"` are P3.3's four tax nodes.

`presence: "required"` is declared for exactly the five nodes whose statement row is ALREADY mandatory downstream — `cash.cfo`, `cash.ending_balance`, `statement.cash_flow_start`, `statement.finance_expense`, `statement.finance_income`, the convergence contract's active-SCC members that `model_ir_v3` binds through `statementRowFor` and where a missing row throws at proof-contract compile time. Declaring them required moves that failure to the earliest responsible layer and types it; it cannot block a case that did not already fail harder later. Every other statement realisation is `case_optional`.

One role-name collision is live and is DECLARED rather than mistaken for a join: `interest.income` carries the role `interest_income` and so does an income-statement row, but that row's economic realiser is `statement.finance_income`. `interest.income` therefore declares `role_collision_owner: "statement.finance_income"`, and a `schedule_row` entry that names an owner which does not actually bind that row is a typed violation (D7).

## How drift between graphs is now caught

Nine typed obligations, each recomputed rather than trusted, split across two channels so the existing mutation harness keeps its shape:

- **Compile channel (typed violation → `BLOCK`)**, reconciling the register against the graph and the case: `ECONOMIC_BINDING_UNDECLARED_NODE`, `ECONOMIC_BINDING_DECLARATION_ORPHAN`, `ECONOMIC_BINDING_ROLE_DISAGREEMENT`, `ECONOMIC_BINDING_REQUIRED_ROW_ABSENT`, `ECONOMIC_BINDING_AMBIGUOUS_ROW`, `ECONOMIC_BINDING_ROW_CONTESTED`, `ECONOMIC_BINDING_COLLISION_OWNER_INVALID`.
- **Artifact channel (`validateLayeredGraphConstitution`)**, re-checking the persisted artifact against itself and consulting only the artifact — deliberately NOT the register, because the compiler accepts an injected register for adversarial testing and a validator that reached for the module default would report the injection rather than the artifact: a claim of `bound` must be carried by a real edge onto a real statement node whose `section`/`semantic_role` match the claim, and **a claim of `row_absent` must be EARNED** — the statement layer may not contain the row the node says is missing. That last clause is what closes R4: absence cannot be manufactured by drifting a row's `semantic_role`, because the validator re-derives presence from the layer. `row_ambiguous` is a separate status for exactly this reason: calling a duplicated row "absent" would have let the duplicate restore the silence.
- **Import channel**: `assertValidEquationGraphRowBinding(ECONOMIC_STATEMENT_BINDING, EQUATION_GRAPH)` runs at module load, so no module in the repository can load against an equation graph whose node set the canonical relation does not cover. Adding a node, removing a node, or renaming a role now fails the repository at import unless the relation is updated with it.
- **Seal**: `economic_binding_scope`, `economic_binding_sha256` and `economic_coverage_sha256` are in the closure core, so the register and the ledger are hash-bound into `closure_sha256`, which the semantic manifest embeds.
- **Manifest leg**: `compileSemanticManifest` now reads `economicStatementBindings(constitution)` and refuses, typed as `ECONOMIC_GRAPH_STATEMENT_BINDING_ABSENT` (following P3.6a's precedent), to seal a manifest that lacks a statement row the constitution reports as bound. The suite additionally proves set equality of (`section`, `semantic_role`) between the manifest's `statement_row` nodes and the layered statement layer on both fixtures, and that the manifest embeds the very closure hash the proof covers.
- **Connectivity, not adjacency**: the suite proves every bound statement row also carries its `projects` edge from the row-plan layer and exactly three `writes_period` edges from the forecast layer — so an economic node reaches the physical projection and its period writers through the statement hub, rather than merely sitting next to them.
