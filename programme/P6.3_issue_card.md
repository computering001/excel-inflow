## Why stage 4's shape verbatim, and why the graph does not enact reuse

`runNode` takes stage 4's `checkpoint()` call shape verbatim — `{ id, recipe, inputs, outputs, action }` — injects the same two ambient components stage 4 injects, keeps the same `reused`/`executed`/`receipts`/`timings` bookkeeping, and returns stage 4's `{ ok, receipt, reused }` (extended with `decision`, `reason`, `moved`, `output_digest`, `duration_ms`, `value`). An operator who can read a stage-4 checkpoint receipt can read an evidence-node receipt.

`ENACT_EVIDENCE_REUSE = false`. A node's action runs on every pass and a HIT means "the cache key agreed", not "the work was skipped". Two arguments, and the second is the stronger:

1. Skipping upstream work changes WHAT IS COMPUTED, and P6.3 is additive by constitution.
2. Because the action always runs, every HIT is CHECKED against a real recomputation: the freshly computed output is digested and compared with the digest the receipt recorded. A cache key that agreed while the output moved is a DISHONEST key and is recorded as `invalid.output_digest_mismatch`. An enacting cache cannot notice that at all — it would serve the stale answer silently. P6.4 therefore inherits cache keys whose honesty has been MEASURED rather than assumed.

## The reason vocabulary

Closed, three-category, and pinned by the suite (every listed reason must have a producer in the module; every recorded reason must be in the list).

- HIT — `hit.inputs_unchanged`, `hit.stage_receipt_reused`
- MISS — `miss.no_prior_receipt`, `miss.recipe_changed`, `miss.input_component_moved`, `miss.dependency_output_moved`
- INVALID — `invalid.receipt_unreadable`, `invalid.receipt_schema_superseded`, `invalid.receipt_foreign_run`, `invalid.receipt_not_success`, `invalid.receipt_tampered`, `invalid.output_digest_mismatch`, `invalid.output_not_hashable`, `invalid.node_threw`

Decisions are written to `<run>/stages/_work_graph/decisions.json` (schema, run identity, closure digest, `enacts_reuse`, the vocabulary, a hit/miss/invalid summary, and one record per node carrying `decision`, `reason`, `moved`, `key_components`, `invalidated_by` and `duration_ms`). Node receipts are written to `<run>/stages/_work_graph/<node>/_receipt.json`, hash-sealed over their own body.
