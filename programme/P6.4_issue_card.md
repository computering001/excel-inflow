## What was chosen for `reused_stages`, and why it had to be the hoist

The work order offered two routes: hoist the reuse checks above the unconditional work, or stop claiming reuse the run did not perform. The second route was NOT AVAILABLE. Four registered suites pin the membership of `reused_stages` on a warm run — `run_user_flow_tests.mjs:343` and `:355`, `run_stage_recipe_tests.mjs:656`, `run_stage4_checkpoint_tests.mjs:154`, `:232`, `:308` — and none of those files is this package's to edit. Narrowing the claim would have turned six green assertions red, and weakening them to fit is exactly what a validator may never do. So the claim had to be made TRUE.

It is made true in two different ways, because the two stages are not the same problem.

`decisions` is HOISTED and genuinely ENACTED. Stage 3's cache key is `{ stage2_receipt, answers, runtime, carrier }`: the stage-2 receipt hash, the answer FILE's hash, the runtime closure digest and the carrier migration input. Not one of those four needs the answered-case recompile or the decision replay to exist — the answer file is hashed straight off disk. The key is now computed first, `readUsableStage` is asked first, and the answered-decision branch is guarded by the answer (`if (!cached3.reusable && intakeResult.outcome === "questions")`). MEASURED after: all eight `decisions` nodes record `hit.stage_receipt_reused` with `executed: false`, and the stage reports `mode: "enacted"`, `skipped: 8`, `executed_ms: 0`, against 228.3ms before.

Two properties make the hoist safe rather than merely faster, and neither is an argument about intent. A stage receipt is only resumable when its status is `success` (`verifyStageReceipt`), so a stage that stopped for questions or blocked on an incomplete answer file can never be skipped here — those exits keep their original position, ABOVE the check. And the work now skipped is work whose result the reuse path already discarded: `answeredCase` was read back from the cached `model-case.json` either way.

## Why one stage is enacted and one is verified, and why `ENACT_EVIDENCE_REUSE` stays false

`evidence_review` cannot be hoisted, and the reason is structural, not an omission. Its own cache key includes `broker_confirmation`, a hash of an artifact its own work produces, so the key cannot be computed before the work runs. And the value it hands downstream — the intake plan — carries live option handlers, which no persisted artifact can hold: `runIntake` is not stage-2 work being redone, it is the REHYDRATION of a non-serialisable output. P6.3's own suite pins that (`intake_plan` must record `hit.inputs_unchanged` on the warm end-to-end run), so skipping it would have broken the package this one inherits from.

The honest resolution is not to pretend, and not to drop the claim, but to make the claim CHECKABLE. `reuseClaimLedger` classifies every node in a claimed stage as `skipped` (never ran), `verified` (ran and reproduced EXACTLY the output digest the receipt it rests on recorded), `degraded` (ran, threw, produced no output either time — the controller's own recorded degradation) or `unrecorded` (ran with no prior recorded output to be measured against). The refusal is confined to what is PROVABLY false: a node that ran, HAD a recorded output to contradict, and contradicted it. `finish()` refuses that run. A claim that merely cannot be checked is reported as `unverified` rather than refused, so a first-ever node execution inside a still-valid stage receipt does not kill a production run. `evidence_review` therefore reports `mode: "verified"` with `executed_ms: 884.5` — the cost is no longer invisible, and the claim is no longer unfalsifiable.

`ENACT_EVIDENCE_REUSE` was NOT flipped. P6.3's argument for it is the stronger one and survives this package: because a node's action always runs when the node is ENTERED, every HIT is checked against a real recomputation, and a cache key that agreed while the output moved is recorded as `invalid.output_digest_mismatch` rather than served. Enactment here is at STAGE granularity — fewer nodes are entered at all — which is exactly what P6.3's `reuseStage` already models and records with `enacted_reuse: true`. Flipping the constant would have removed the recomputation check that makes the enactment safe, and would have made P6.3's pin red for no gain.

The scope column is COMPUTED from the corrected invalidation map, not restated, and every `reason_code` and `terminal_state` is a name that already exists in `assets/terminal-reason-registry-v1.json` (READ, never written); `validateErrorClassificationTable` refuses an invented reason code, a terminal state outside that code's `allowed_terminal_states`, and any breach of the registry's own `category_to_user_owned_terminals` firewall.

Two findings the table produced rather than assumed. The registry has exactly two `SOURCE.*` codes, both specific, and no generic "the supplied evidence could not be parsed" code — so `malformed` binds to the nearest lawful existing code and the addition is recorded as owed rather than invented. And six of the nine classes land on `INTERNAL.compiler_or_graph_defect`, which is the registry's own `migration_wiring_status` speaking: the outcome-compiler rewiring is declared Phase-6 work and has not happened.

## Attempt receipts, and the retry idempotency proof outside the broker lane

Every evidence work node execution — first try or retry — now writes an attempt receipt to `<run>/stages/_work_graph/attempts.json`: label, attempt number, status, duration, error class, reason code, terminal state, cache-reuse rule, computed downstream invalidation scope, remaining retry budget, input digest, the FIRST attempt's input digest, output digest, and the refusal if there was one. The refusal vocabulary is closed (`attempt.unclassified_error`, `attempt.retry_budget_exhausted`, `attempt.retry_input_moved`, `attempt.retry_not_idempotent`, `attempt.class_forbids_retry`).

Idempotency is CHECKED, not assumed, in two directions. A retry is refused if its input digest differs from the first attempt's under the same label (`attempt.retry_input_moved`) — a retry of different work is not a retry. And a second success under the same label whose output digest differs from the first is refused (`attempt.retry_not_idempotent`). The suite proves it on the real path: the same node driven through the real `createEvidenceWorkGraph` with a transient failure on attempt 1 produces the same output digest as the control run that never failed, seals exactly ONE node receipt (`status: success`), leaves exactly ONE decision record, records exactly two attempts, and stops at exactly two retries when the failure never clears. The lane is the evidence half, deliberately outside the broker supervisor.

An unclassified error is REFUSED — recorded with the repair it needs, never retried, never mapped to a terminal outcome, and then RETHROWN UNCHANGED so the controller's existing handling is not altered. That refusal fires on a REAL production throw: `broker_preview` throws `The "data" argument must be of type string...` on the acquisition fixture, and the ledger now records `attempt.unclassified_error` against it. That is a finding, not a fixture — a live untyped throw in the controller's silent degradation path.
