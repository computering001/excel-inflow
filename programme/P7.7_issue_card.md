## The design decision, and why

**A second workflow file, not a `schedule:` bolted onto the merge gate.** Adding `schedule:` to `read-only-development-gate.yml` would fire all seven lanes, the serial registry and the 90-minute package compile on every cron unless every job carried an `if:` guard — and a gate whose tier membership lives in eleven hand-written conditionals is exactly the shape that lets a tier stop running without anyone noticing. A separate file makes the tier boundary structural, lets the merge gate's content stay byte-identical, and lets the governance suite hold two DIFFERENT pin sets.

**Roles are declared, not inferred.** The governance suite used to loop over every workflow file asserting merge-gate properties, which had the side effect of forbidding any scheduled workflow from existing. It now reads the role of each file from `assets/ci-gate-tiers-v1.json`, pins declared-roles against files-on-disk in BOTH directions, and applies role-specific pins. A workflow cannot escape a pin set by being undeclared, and a scheduled gate that also declares `pull_request:` is refused as a masquerade.

**Quarantine is enforced by the validator, never by a hand-edited `continue-on-error`.** The deep gate's frozen-cohort job asks `run_ci_gate_tier_tests.mjs --verdict-for-job` for its verdict. That mode first validates the whole register — so an expired or unowned entry anywhere makes the verdict itself fail — then suspends the job's failure ONLY if an unexpired, owned entry names that exact job. Because the register's health is also a merge-gate job, an expiry that lapses turns the pull-request gate red. A quarantine therefore cannot sit silently: it has an owner, a date, and a deadline that breaks the build.
