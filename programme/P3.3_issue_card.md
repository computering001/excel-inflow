## Which graph the acyclicity is proven over, and why

Over the canonical single-period template `assets/equation-graph.v1.json` — because that IS the case's own equation graph. There is no per-case graph: `solveCase` compiles `equation_graph_evidence` from this one asset for every case, and the convergence contract hash-binds it, so a case cannot be solved against any other graph. The suite closes that loop rather than asserting it: it solves both certified fixtures and asserts `evidence.graph_sha256 === proof.graph_sha256`, then asserts no ETR node appears in the solved SCC evidence or in the solver's iteration state vector. The proof is therefore about the graph the case actually solved against, established by hash rather than by resemblance.

## How acyclicity is proven

Six independent obligations, each recomputed in the suite rather than read off the proof object:

1. PRESENT — each of the four declared roles binds to exactly one node (roles, not id prefixes: the validator already enforces role uniqueness, so a role names one node by construction).
2. WIRED — all six declared edges exist with exactly their declared `from`/`to`/`type`/`activation`.
3. CONNECTED — the rate and the base each reach the charge, and the charge reaches the sink. Without this, 4–6 would be vacuously true of four isolated nodes.
4. ACYCLIC INTERNALLY — a deterministic Kahn topological order exists over the induced subgraph in the structural graph and in BOTH circularity states. A returned order is the certificate: Kahn places every node exactly when there is no cycle, and the suite re-verifies the order is genuinely topological (every internal edge runs forward in it).
5. OUTSIDE EVERY SCC — no strongly connected component of the WHOLE graph (structural, circularity 0, circularity 1) contains any ETR node. This is the DAG-safety statement itself: a node inside an SCC is solved by iteration, which is precisely what the `tax`/`rate` pair must never require.
6. SINK — no edge leaves the ETR node set. With 5 this makes the acyclicity structural rather than incidental: the tax path cannot join a cycle without an outgoing edge, and adding one fails here.

The reason 5 and 6 hold is economic, not accidental, and the suite says so: this graph's cash flow starts at EBIT (`edge.ebit_to_cash_flow_start`), so tax sits outside the cash bridge. Wiring net income into `statement.cash_flow_start` would close net income → cash flow start → CFO → ending cash → cash interest income → interest income → net interest → pre-tax income → tax → net income. That is a real circularity, it is the mistake this invariant exists to stop, and the suite drives it as a mutation: it is caught twice (SCC trap and sink violation), refused by `validateEquationGraph`, and refused by the proof compiler.
