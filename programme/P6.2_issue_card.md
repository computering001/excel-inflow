## The recipe, exactly

`user-stage-recipe/1.0`, embedded in every receipt as `recipe`:

- `stage_id`, `controller_version`
- `code_closure_sha256` — the digest of the DERIVED executable closure (284 members of the 332 declared runtime-code members), not a hand-maintained list
- `code_closure_member_count` — so a closure that silently shrank is visible even if the digest is not compared
- `policy_versions` — `runtime_integrity_schema` and `runtime_budget_policy_schema` supplied by the caller, plus `flow_schema`, `stage_receipt_schema`, `visible_journey_contract` and `workflow_state_contract` written by `flow_runtime.mjs` AFTER the caller's map, so a caller cannot shadow or understate them
- `input_digest` — `hashValue(input_hashes)`
- `recipe_sha256` — the digest of all of the above

Older-receipt refusal rule: `user-stage-receipt/1.0` is listed in `SUPERSEDED_STAGE_RECEIPT_SCHEMA_VERSIONS`. Such a receipt is READ and REPORTED — the miss record names the schema it found — and then REFUSED for reuse, never reinterpreted. It cannot honestly be reinterpreted: a /1.0 receipt records no closure digest, no policy versions and no input digest, so filling them in from the current run would fabricate exactly the agreement the field exists to check. A current-schema receipt that carries `recipe: null` is likewise never reusable.

## How the closure is derived, and what the closure test asserts

Derivation (`deriveStageRuntimeClosure`, user_flow_controller.mjs): start at `scripts/run_user_flow.mjs` and `scripts/orchestrate_release.mjs`; follow every path-shaped executable token (`*.mjs|cjs|js|py`) transitively, resolved by BASENAME against the declared runtime-code inventory; add every vendored `node_modules/**` member; add every non-JavaScript declared member. One token regex covers both edge kinds the closure has — the literal import specifier and the process spawn — because both spell the file out, and basename resolution admits every candidate, so the scan is a deliberate over-approximation that can only widen the closure.

`scripts/lib/release_js_import_scanner.mjs` is used by the SUITE, not by the controller: it is not a declared runtime member, and the release compiler reconciles `script_allowlist` against the import closure in both directions, so a shipped module may only import shipped modules. (This was discovered the hard way — the first implementation imported it and the derivation correctly failed closed on its own edge.) The suite therefore proves the wider production scan admits everything the authoritative grammar finds:

- transitive closure: for all 98 executable JavaScript members, every literal relative specifier resolves inside the declared inventory AND is itself a member (0 unclosed edges, 0 escaping edges)
- no member has a non-literal dynamic import, so no member's edges are unenumerable
- every bare, non-`node:` specifier (`jszip`) maps to a vendored package whose every byte is a member
- the historical hand list is a member subset that omitted 68 executed modules — RED 2, pinned
- no instruction file is a member; the excluded set (60 files) is ONLY instruction files (12) and unreachable JavaScript (48) — no asset, no Python module, no vendored byte is dropped
- the derived digest is INSENSITIVE to a SKILL.md edit while the old catch-all rule IS sensitive — RED 3, pinned in both directions
- the derived digest is SENSITIVE to a byte change in `solver.mjs`, `orchestrate_release.mjs`, `emit/plan.py`, `model-case-v2.schema.json` and `jszip.min.js`
- the derivation is deterministic, and an undeclared entrypoint or a missing inventory fails closed

## The build_checks narrowing, and why it is correct rather than merely narrower

`build_checks` moved from 333 files (everything declared except `references/`) to the same 284-member derived closure the other four stages use. Exactly 60 files were dropped, in two classes, each with its own argument:

1. **12 instruction files** (`SKILL.md`, `references/**`). `scripts/lib/source_identity.mjs` — THE single definition of runtime-code-closure membership, consumed by both the release compiler and the runtime-isolation validator — already refuses instruction files as closure members by construction. They are absent from `integrity.runtime_code_closure` before this package touched anything. Dropping them removes a build input the repository's own membership authority says is not executable.
2. **48 unreachable JavaScript files** (test harnesses, `run_excel_inflow_vnext.mjs` and its ingress-side libraries: `attachment_ingress`, `support_envelope`, `performance_receipt`, `broker_supervisor`, `progress_heartbeat`, `raw_canary_fixture`, ...). Node cannot execute a module that is not reachable by a literal import/require/dynamic-import edge from an entrypoint; the only other execution edge is a process spawn. Both edge kinds are followed, and the two holes that would break the argument are closed by proof rather than assertion: no member has a non-literal dynamic import, and no member's literal specifiers leave the member set. The vnext-side modules run in the PARENT process before and after the delegate; their bytes cannot change a stage output given the same stage inputs, and those inputs are hashed.

The narrowing deliberately does NOT touch the case P6.1's card warned about. `semantic_graph.mjs`, `row_plan.mjs` and the extractors are genuinely reachable from the build entrypoints, so they remain build inputs and a mid-edit tree still cold-starts stage 4 — correctly. What no longer cold-starts it is a README edit or a test-harness edit. Net direction across the five stages: stages 1, 2, 3 and 5 were TIGHTENED from 13-18 hand-named files to 284 derived members (68 executed modules per stage newly guarded); stage 4 was narrowed by 60 files, all of them provably unable to affect it.

## The run_store.mjs verdict

`RunStore` is DEAD. Declared here explicitly, and pinned by a check in the new suite that fails if it ever acquires a caller (so the claim cannot go stale silently). Justification: it is a node-keyed content-addressed receipt store with zero writers, so any reader would read an empty tree; its `/workspace/run/<run_id>/<node>/` layout is superseded twice over by `release_checkpoint_store.mjs` (stage 4's 14 checkpoint ids, correct and recipe-versioned) and by `user_flow_controller.mjs`'s stage receipts (now recipe-versioned too); and `resolveRunRoot`'s silent fallback to `os.tmpdir()` is the opposite of the run-identity discipline P6.1 established. It is a v3.8 deletion candidate — the class, `resolveRunRoot`, and `RECEIPT_FILE`.

The same file's `nodeInputDigest` and `explainMiss` are NOT dead and are now LIVE. They were written for exactly the thing the invariant demands — "a cache miss can be explained rather than merely observed — `explainMiss` below diffs two of these and says which component moved" — and had no caller. `readUsableStage` now builds a `nodeInputDigest` over the named components of a stage's key (recipe, executable closure, input files, policy params, previous receipt and each declared output) and writes `stages/<id>/_miss.json` whenever a stage is not reusable, carrying the moved components, the refusal reasons, and the recipe and schema it FOUND versus the recipe it wanted. `run_store.mjs` was therefore given its caller without being edited.
